# 系统架构

## 设计目标

系统以“证据先于答案”为第一原则。文本制度和统计表格分别解析，在证据层统一；确定性取数和计算不交给生成模型猜测。

## 逻辑架构

```text
原始文件（只读）
  → 文件台账、哈希、去重、版本元数据
  → 格式路由与旧格式转换
  → 文本条款库 / 表格事实库
  → PostgreSQL + Qdrant 混合索引
  → 问题分类、条件抽取和查询计划
  → 稀疏/稠密召回、过滤、重排
  → 证据充分性和冲突检查
  → 确定性取数/计算或受控生成
  → 数字、实体、规范强度校验
  → 答案、引用、警告、澄清或拒答
```

## 组件

- `frontend`：用户问答、证据查看、知识库管理、入库状态和评测结果。
- `backend`：API、业务规则、解析、入库、检索、模型编排和评测。
- `postgres`：文档台账、结构化表格事实、用户、问答、反馈和评测。
- `qdrant`：稠密/稀疏向量、元数据过滤和混合召回。
- `model endpoint`：OpenAI-compatible 本地或云端推理服务，不与业务代码耦合。

## 当前离线检索基线

解析产物会转换为统一 `knowledge_chunks`：

- Word 普通段落：保留段落序号、样式、标题层级路径、条款号和长文本分片。
- Word 表格：按行组织表头和值。
- PDF：按页提取文本并保留页码，长页面分片。
- Excel：按工作表行组织单元格地址和值，同时附带表头与最近分组上下文。

稀疏检索采用可完全离线复现的字符二元组召回、标题/文件名候选过滤、数值意图和单元格标签加权。配置 Embedding 后，系统同时向 Qdrant 发起稠密召回，再使用加权 Reciprocal Rank Fusion 合并两路排名。问题明确指定《文件名》时，向量召回按候选文档 ID 过滤。Embedding 或 Qdrant 不可用时自动退回稀疏检索并返回警告。

向量点使用知识块 ID 派生的确定性 UUID，因此重复执行建库命令是覆盖写入，
不会产生重复点。Embedding 向量只保存在 Qdrant，原始内容仍以业务库中的
知识块为准。

## 可审计回答链路

回答编排先判断证据类型：

1. Excel 行证据包含目标列、数值和单元格地址时，由确定性逻辑选择单元格、继承表头单位并直接回答，不调用生成模型。
2. 文本证据交给 OpenAI-compatible 模型时，模型只能返回 `answer` 和 `citations` JSON。
3. 后端校验引用编号范围、正文引用标记，以及答案中的数字是否存在于证据。
4. 模型超时、协议异常、JSON 非法、引用越界或出现证据外数字时，响应自动降级为原始证据模式。
5. 没有检索证据时明确拒答，不调用模型补全。

接口同时返回 `answer_mode`、结构化 `citations`、`warnings` 和
`trace_id`，便于前端解释、日志追踪和后续评测。

## 数据边界

- `/data/raw`：甲方原始文件，只读。
- `/data/derived`：转换文件、结构化解析结果、manifest 和中间结果，可重建。
- PostgreSQL/Qdrant：运行态索引，可从 manifest 和解析结果重建。

## 证据定位

- Word：文件、章节路径、条款号、段落序号。
- PDF：文件、页码、条款号、页内文本片段。
- Excel：文件、工作表、表名、多级表头路径、行列维度、单元格地址、单位和期间。

## 模型解耦

Provider 层只依赖 OpenAI-compatible HTTP 协议。模型选择、Base URL 和凭据来自环境变量。系统在模型禁用时仍可完成文件台账、解析、结构化查询和评测数据管理。

模型只接收当前问题和 Top-K 证据，不接收完整原始目录。使用云端 Provider
仍代表这些问题与证据片段会离开指定环境；使用本地 Provider 时数据可保持在甲方环境内。
